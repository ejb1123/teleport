# Latency and stability review — 2026-10

Source review of the capture → encode → transport → decode → present and input
paths, aimed at parity with gaming streamers (Parsec, Moonlight/Sunshine, Steam
Link). Each finding was checked against the code at `5b2be8a`. Line numbers refer
to that commit. This is a code review, not a measured latency benchmark.

Severity: **Critical** = session loss or a frozen picture from a single ordinary
event; **High** = latency/stability gap a gamer would notice, or a missing
safeguard; **Medium** = efficiency/quality; **Roadmap** = new capability.

Status: `open`, `fixed` (in this branch, with verification noted), `deferred`
(reason given).

### R6: end-to-end encrypted relay

Goal: when direct UDP fails, relay through a Cloudflare MoQ relay (draft-14/16;
`moq-net` has an IETF adapter) without the relay seeing content.

- Through a relay, QUIC TLS terminates at the relay. The host certificate pin no
  longer authenticates the host, so content needs object-level encryption.
- Handshake over a handshake track pair: host signs with its existing identity
  key (fingerprint trust unchanged); client proves its device credential.
  Code pairing (SPAKE2) and OPAQUE are already safe over untrusted channels;
  PAM login must move inside the E2E channel.
- Per direction/track keys via HKDF; AEAD (`ring`) every object. Nonce from
  track/group/object numbers; AAD binds track name, group, object, session ID.
  Replay window on input; rekey on reconnect and by volume.
- Use the same layer on direct connections: one audited code path.
- The relay still sees IPs, object sizes and timing (input timing reveals
  typing cadence). Opaque track names; optional constant-rate padded input.
- Direct first, relay fallback. Datagram and priority behaviour through the
  relay is not documented: keep a reliable input fallback. Expect +5–30 ms.
- New security-critical code: needs its own review before enabling.

### Desktop audio (M8, 2026-10-16)

`audio_end_to_end_latency` (tests/audio_latency.rs) plays a 440 Hz tone with
a 2 kHz tick every 500 ms into a private PipeWire null sink; a real host
captures its monitor, a windowed client (Xvfb) plays into a second null sink,
and both monitors are recorded in one pipeline. Latency is tick to tick
(capture, encode, network, decode, playout); dropouts are silent gaps of
2 ms or more in the played tone. `TELEPORT_TEST_NETEM` runs host and client
in a netns behind `tc netem`. Release builds, interleaved, three runs per
row, load 13–18 on 8 cores:

| Link | Before p50 / p95, dropouts | After p50 / p95, dropouts |
| --- | --- | --- |
| clean | 98–119 / 107–129 ms, 1 | 77–82 / 81–85 ms, 0 |
| 10 ms ± 5 ms jitter | 91–101 / 114–132 ms, 4–6 | 73–90 / 73–90 ms, 0–1 |
| 10 ms, 2% loss | 99–102 / 120–132 ms, 2–6 | 72–89 / 72–89 ms, 0 |

Before, packets were timestamped on arrival (`do-timestamp`), so the
sink's playout point wandered with arrival jitter (p95 30 ms above p50 within
a run) and resynchronised with gaps. Even on loopback, packets arrive up to
~100 ms late in bursts, mostly from the PipeWire quantum on the capture side.
After:

- Packets are timed by MoQ group sequence (one 10 ms packet per group). A
  packet later than 10 ms moves playout later by its lateness at once; when
  every packet of a 2 s window arrived early by more than 2 ms, playout moves
  back. Latency settles at the jitter actually seen and stays there.
- A missing sequence number or a moved playout leaves a hole that is sent to
  `opusdec plc=true` as a GAP event. A timestamp hole alone does not trigger
  PLC (tested: `gap_events_are_concealed_by_opus_plc`).
- On Linux the client plays through `pulsesink buffer-time=40000
  latency-time=10000` instead of `autoaudiosink` (pulsesink defaults to a
  200 ms buffer). Alone, with arrival timestamps, this cut p50 by ~35 ms but
  added dropouts under load; with the playout timeline it has none.

Not applicable: Opus in-band FEC (LBRR) exists only in SILK, and the encoder
is CELT-only (`restricted-lowdelay`); switching modes adds ~4 ms of
look-ahead. The 10 ms frame size is unchanged.

Tried and rejected:
- Host `pulsesrc buffer-time=10000 latency-time=5000` (from 20/10 ms): no
  lower latency, more dropouts (10–22 against 1–5 at the same load).
- A fixed timeline anchored at the first packet, dropping late packets and
  re-anchoring after three: a start-up burst stayed as 30–50 ms of extra
  latency, and each dropped packet was a gap.
- A 40 ms client queue (from 100 ms): it helped only with arrival
  timestamps; with the timeline the queue holds audio scheduled up to 100 ms
  ahead, so it stays at 100 ms.
- Sending the previous packet along as redundancy: not built. QUIC
  retransmits lost packets, so loss arrives as lateness, which the timeline
  absorbs (2% loss: no dropouts).

For reference, a plain `pulsesrc → pulsesink` loop between the two null
sinks measures 60–123 ms (default sink buffer, varying per run), so most of
the remaining latency is the audio server and the sinks.

### High refresh rates (R7, 2026-10-16)

Host: `high_rate_capture_benchmark` (release): a 2560x1440 GPU-exported

| Rate | Encoded / captured | Capture→packet | Submit→packet | CPU per frame |
| --- | --- | --- | --- | --- |
| 60 | 100% | 4.6–5.0 ms | 4.5–4.7 ms | 1.5 ms |

Real desktop (`portal_capture_benchmark`, `TELEPORT_BENCH_FPS=180`, own
portal session on KDE Plasma 6.7, 179.96 Hz monitor, load ~10): KWin
negotiated `max-framerate=179/1` (it rounds the refresh rate down and never

screencast and offers 179 to a 180 Hz client. Animated content was not
generated on the user's desktop.

| Output | Frames/s | Mean / p95 per frame |
| --- | --- | --- |
| GPU frame (zero-copy CUDA→GL presentation) | 432 | 2.3 / 2.5 ms |

Not verified: a real 180 Hz session with moving content end to end, VRR

### Peer-to-peer through NATs (R8, 2026-10-16)

`tests/p2p.rs` builds, in unprivileged user and network namespaces, a host
and a client each behind its own Linux MASQUERADE NAT (5 ms access links) and
a relay 15 ms further away, so ~20 ms RTT between the peers and ~80 ms via
the relay. The client's direct address is the host's private one
(unreachable). Debug build, two serial runs each, load average 5.4–8.4:

| Scenario | Path | Connect (s) | Probe p50 / p95 (ms) |
| --- | --- | --- | --- |
| Cone NATs with router firewall | p2p, server-reflexive | 1.33–1.36 | 23.2–24.0 / 24.1–27.2 |
| Cone NATs without inbound firewall | p2p, server-reflexive | 1.32–1.35 | 23.2–24.0 / 25.2–28.6 |
| Client NAT symmetric (`--random-fully`) | relay | 3.57–3.64 | 84.2–87.5 / 86.2–94.3 |
| Peer UDP blocked | relay | 3.60–3.63 | 87.4–87.5 / 94.5–95.6 |
| Host `--no-p2p` (as an older host) | relay | 3.42–3.45 | 84.1–87.3 / 86.4–93.6 |
| Client `--no-p2p` (previous behaviour) | relay | 3.43–3.47 | 85.1–87.2 / 88.3–92.9 |

- Connect: peer-to-peer runs alongside the 2.5 s direct attempt, so it
  connects ~2.1 s sooner than the previous relay fallback here. Of its
  ~1.3 s, ~1.15 s is relay signalling (five relay messages, each an announce
  and subscribe round trip); the punched QUIC handshake takes ~60 ms.
- Failure cost: when signalling succeeds but punching cannot (symmetric NAT,
  blocked UDP), the relay starts 0.1–0.2 s later than before (signalling plus
  the 1.5 s dial window end after the direct attempt). Hosts that do not
  answer cost nothing extra: their silence overlaps the direct attempt.
- Input round trip drops by the relay detour (86 → 24 ms here; real relays
  add 5–30 ms per the comparison).
- Without an inbound firewall, Linux conntrack records an unsolicited punch
  and then remaps the client's port when the client's own packets go out;
  with full-TTL first punches that run fell back to the relay. The host's
  first punches now carry TTL 2 (per datagram, `IP_TTL` cmsg), which opens
  its own NAT and expires before the client's.

### Capped links and loss recovery (G6/G7, 2026-10-17)

`tests/network.rs` now runs 20 s profiles (`snow`, 1280x720 at 30 FPS,
libx264 → software decode, release build) and reports, per run: throughput
over the second half against the bottleneck (`util`), capture→ready p50/p95
(both ends stamp and read the Unix clock with `TELEPORT_TEST_WALL_CLOCK=1`;
one machine), freezes (gaps over 100 ms: count and total), the longest gap,
and keyframe sizes against the mean delta frame. New profiles: 10 and
5 Mbit/s with ~120 ms bottleneck queues (`limit 150`/`75`), 1.2 Mbit/s,
10 Mbit/s with 2% loss, Wi-Fi-like (25 Mbit/s, `slot 2ms 12ms`, Pareto
jitter, 0.5% loss) and a 400 ms total-loss burst on a 20 ms RTT link
(recovery = longest gap − 400 ms). Each part can be switched off for A/B
runs: `TELEPORT_NETWORK_FEEDBACK=0` (host), `TELEPORT_INTRA_REFRESH=0`
(host).

**G6: rate control from client delay feedback, and step-down.** Before, the
host cut on its own QUIC RTT, which never sees the queue that matters: QUIC
paces at its congestion window, so an encoder running above the link fills
the host's send buffer, not the network. Now the client measures, for every
frame, its first byte's arrival against the host's send timestamp (offsets
cancel against the minimum over 10–20 s), and sends the lowest queueing
delay of each 100 ms plus the received rate over 500 ms
(`Event::NetworkFeedback`, only to hosts advertising `network_feedback`).
The host (`congestion::DelayRateController`): two intervals at 30 ms or
more of queue, and less arriving than encoded over the last second, cut to
85% of what the busy link delivered (later cuts at most half, so a stalled
client is not mistaken for a 0 kbit/s link); a queue that is not ours backs
off 10% after half a second. It probes +8%/300 ms while far from the last
bottleneck estimate and +2% near it, forgets the estimate 5 s after the
last overflow, and ignores the queue its own keyframes build for their
transmission time. Under 0.05 bit per pixel (H.264; two thirds for H.265)
for 4 s, `congestion::Ladder` restarts the stream at 75%, then 50% width,
then half the frame rate, at most every 8 s; it steps back up after 10 s at
1.4× the floor above. The negotiated stream and the user's bitrate are the
ceiling. F8 shows "Network step-down". Old clients keep the RTT controller.

Two runs per variant, interleaved, load 4–20 on 8 cores:

| Profile | Before: util / p95 / freezes (ms) | After: util / p95 / freezes (ms) |
| --- | --- | --- |
| 10 Mbit/s, 120 ms queue | 50–57% / 483–527 ms / 113–331 | 75–81% / 365–375 ms / 0–149 |
| 5 Mbit/s, 120 ms queue | 36–39% / 1148–1293 ms / 2937–2987 | 57–79% / 966–1283 ms / 958–1903 |
| 3 Mbit/s, deep queue (old `capped`, 640 wide) | 23–24% / 865–926 ms / 354–360 | 70–74% / 691–715 ms / 0–103 |
| 1.2 Mbit/s (8 Mbit/s asked) | 27% / 1628 ms / 14013 (one of two runs survived) | 77–81% / 1694–2050 ms / 10370–11964, stepped to 960 and 640 |
| 10 Mbit/s, 2% loss | 82% / 106–112 ms / 711–1247 | 85% / 112–157 ms / 1056–1632 |
| Wi-Fi-like | 80–83% / 68–89 ms / 345–399 | 85% / 46–61 ms / 0–544 |

The p95 on the narrow links is still dominated by the first seconds, when
the session starts at its full bitrate (8–16 Mbit/s) into the bottleneck.
Under heavy machine load (load 25–47) runs of both versions were erratic
(stalled clients look like collapsing links); only the quieter rounds are
in the table.

**G7a: intra refresh instead of periodic IDRs.** libx264 and h264_nvenc
encode with `intra-refresh` and a one-second period; the host then sends no
periodic IDRs (`set_key_interval` is ignored), only the first frame and
requested ones (`forced-idr`). Refresh starts, which those encoders flag as
key frames, no longer start MoQ groups: the host checks the slice type
(`protocol::annexb_keyframe`). H.265 and VA-API/QSV keep periodic IDRs:
FFmpeg's H.265 decoder (also under NVDEC and VA-API) drops every picture
after a missing reference, and FFmpeg exposes no VA-API/QSV intra refresh.
`intra_refresh_heals_a_lost_frame_without_an_idr` checks that a lost frame
heals within the period with refresh and does not without it, and that
IDRs come only at the start and on request (NVENC with
`TELEPORT_TEST_HARDWARE=1`). Three runs each, load 4–18:

| Profile | Periodic IDRs: keyframes / max key ÷ mean delta / p95 | Intra refresh |
| --- | --- | --- |
| 10 Mbit/s | 6 / 3.6–4.4 / 307–466 ms | 1 / 3.2–3.9 / 325–467 ms |
| 10 Mbit/s, 2% loss | 6 / 2.1–2.3 / 89–108 ms | 1 / 1.4–2.1 / 88–112 ms |
| Wi-Fi-like | 6 / 2.1–2.3 / 39–72 ms | 1 / 1.6–1.9 / 48–51 ms |
| 400 ms burst | 6 / 2.2 / longest gap 453–497 ms | 1–2 / 1.8–2.3 / 454–467 ms |

Utilisation and freezes are unchanged within noise. Loss recovery itself
does not change: with one group per GOP the client still abandons the
group and requests an IDR (rate-limited to one per 100 ms); recovery after
the 400 ms burst is 50–100 ms either way.

**R1 (one MoQ group per frame), tried and rejected.** A capability-gated
prototype (`ClientFeatures.frame_groups`): the host wrote each frame as its
own group; the client held a newer group while a frame was still arriving
(200 ms) or an older one could still come (50 ms), decoded through gaps of
up to two frames with concealment (intra refresh repairs them) and waited
for an IDR after longer gaps; the subscription allowed 300 ms per group.
Three runs against intra refresh with GOP groups, load 3–13:

| Profile | GOP groups: p95 / longest gap / Mbit/s | Frame groups |
| --- | --- | --- |
| 5 Mbit/s | 1278–1349 ms / 579–736 ms / 3.8–4.1 | 115–374 ms / 1302–1944 ms / 3.7–4.4 |
| 10 Mbit/s | 334–522 ms / 80–243 ms / 7.8–8.3 | 176–381 ms / 1594–2810 ms / 9.1–9.2 |
| 1.2 Mbit/s | 2397 ms / 1652 ms / 0.93 | 109–565 ms / 10730–11767 ms / 0.95–1.03 |
| 5% loss | 68–96 ms / 107–173 ms / 3.4–3.6 | 24–31 ms / 108–1066 ms / 0.95–2.2 |

Tail latency fell, but every profile gained second-long freezes, and the
narrow link 11 s ones. Causes: moq-lite serves the newest group first, so
frames arrive out of order under any queue; an IDR requested after a gap
can itself exceed the latency budget on a slow link and is requested
again; and FFmpeg's H.264 decoder shows nothing after a gap of more than a
couple of frames until the refresh completes (up to its full period, even
with `AV_CODEC_FLAG2_SHOW_ALL`), while its H.265 decoder never recovers
without an IDR. Not kept. Worth revisiting with a publisher that serves a
track's groups oldest-first within its latency budget, and a decoder that
conceals across longer gaps.

Also tried and rejected: the mean (instead of the lowest) queueing delay per
100 ms interval and a 100 ms received rate (a keyframe's own transmission
read as congestion and the rate collapsed); a first cut limited to half
(starting 8–16 Mbit/s into 1.2 Mbit/s built seconds of backlog, and one
session timed out); cutting on any queue whether or not the link was the
limit (CPU-starved clients drove the rate to the floor).

| --- | --- | --- | --- | --- | --- | --- |

| 40 ms RTT | 0.6 / 0.9 | 20.2 / 20.6 | 0.2 / 0.4 | 0.9 / 1.9 | 22.1 / 23.2 | −0.5 (0.8) |

| Wi-Fi-like, 720p | 3.0 / 7.3 | 16.8 / 33.5 | 1.1 / 2.9 | 1.0 / 2.0 | 22.6 / 41.1 | −3.9 (5.9) |

encode→send is 0.0 everywhere: the encoder thread hands each frame to MoQ
at once, and time in QUIC's send buffer shows up as network. "Clock error"
is the estimate minus the Unix clock both processes share here
(`TELEPORT_TEST_WALL_CLOCK=1`). On symmetric links it is a steady −0.5 ms:
the answer path (host session loop → updates track → reader) is slower
than the probe path. On loaded links it grows to a few ms, because video
queues in the host→client direction only and the RTT/2 assumption breaks;
the max values are the first frames, before the filter has a good sample.
The F8 `clock ±` bound (half the best round trip) covers all of these.

Windowed under Xvfb (`windowed_presentation_latency`, debug build,
1280×720@60, software x264 and decode, SDL software renderer): capture→present
7.2 / 8.3 ms, of which decode→present (upload, draw, swap) 2.0 / 2.7 ms.

Click→changed frame (`flash_on_input_follows_clicks`, 1 ms link, 30 fps
test source): 20.6 / 33.1 ms over 25 clicks. Most of it is waiting for the
next 33 ms capture tick (16.5 ms on average); the rest is the path above.

Not measured here: the display (scanout, panel response), a real KDE
capture, hardware encode/decode, Parsec. The photodiode/camera method in
docs/performance.md covers the first; nothing above replaces it.
