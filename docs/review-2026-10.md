# Latency and stability review — 2026-10

Source review of the capture → encode → transport → decode → present and input
paths, aimed at parity with gaming streamers (Parsec, Moonlight/Sunshine, Steam
Link). Each finding was checked against the code at `5b2be8a`. Line numbers refer
to that commit. This is a code review, not a measured latency benchmark.

Severity: **Critical** = session loss or a frozen picture from a single ordinary
event; **High** = latency/stability gap a gamer would notice, or a missing
safeguard; **Medium** = efficiency/quality; **Roadmap** = new capability.

Status: `open`, `fixed` (in this branch, with verification noted), `deferred`
(reason given).

### R6: end-to-end encrypted relay

Goal: when direct UDP fails, relay through a Cloudflare MoQ relay (draft-14/16;
`moq-net` has an IETF adapter) without the relay seeing content.

- Through a relay, QUIC TLS terminates at the relay. The host certificate pin no
  longer authenticates the host, so content needs object-level encryption.
- Handshake over a handshake track pair: host signs with its existing identity
  key (fingerprint trust unchanged); client proves its device credential.
  Code pairing (SPAKE2) and OPAQUE are already safe over untrusted channels;
  PAM login must move inside the E2E channel.
- Per direction/track keys via HKDF; AEAD (`ring`) every object. Nonce from
  track/group/object numbers; AAD binds track name, group, object, session ID.
  Replay window on input; rekey on reconnect and by volume.
- Use the same layer on direct connections: one audited code path.
- The relay still sees IPs, object sizes and timing (input timing reveals
  typing cadence). Opaque track names; optional constant-rate padded input.
- Direct first, relay fallback. Datagram and priority behaviour through the
  relay is not documented: keep a reliable input fallback. Expect +5–30 ms.
- New security-critical code: needs its own review before enabling.

## Test hygiene (found during this work, not caused by it)

- Nine `media::tests` cases look up the GStreamer-only `video_decoder` element.
  They fail under the default FFmpeg backend with `--include-ignored` on
  unmodified `5b2be8a` too; CI only runs them with
  `TELEPORT_VIDEO_BACKEND=gstreamer`. They should skip or select the legacy
  backend explicitly.
- The legacy decoder-replacement and HDR tests are flaky on unmodified `main`:
  4–5 of 38 failed in each of two full legacy runs ("insufficient sustained
  fresh output", "no decoded HDR frame"). This branch had 1–2 failures in two
  runs and 0 in three more. Their 3 s hardware-decode deadlines look
  timing-sensitive under GPU contention.

## Network baseline (`tests/network.rs`, 2026-10-15, after `ded75c4`)

640×360 at 30 FPS, software encode/decode, 180 frames. RTT is twice the netem
delay. `snow` profiles target 4 Mbps (capped: 6 Mbps).

| Profile | FPS | Mbps | Max stall | Skipped groups |
| --- | --- | --- | --- | --- |
| clean | 30.0 | 0.20 | 61 ms | 1 |
| 100 ms RTT | 30.0 | 0.21 | 46 ms | 1 |
| 1% loss (snow) | 29.4 | 2.97 | 120 ms | 2 |
| 5% loss (snow) | 29.4 | 3.33 | 181 ms | 3 |
| jitter ±15 ms (snow) | 22.3 | 1.58 | 920 ms | 13 |
| 6 Mbps into 3 Mbps (snow) | 14.6 | 0.57 | 2522 ms | 30 |
| 2 s blackout | 22.7 | 0.16 | 2100 ms | 5 |

Random loss is absorbed by QUIC retransmission. Capacity below the configured
bitrate is the real gap: the queue fills and video stalls for seconds (H12).

### After H12 (three runs each)

| Profile | FPS | Mbps | Max stall | Skipped groups |
| --- | --- | --- | --- | --- |
| 5% loss (snow) | 27.7–29.0 | 2.97–3.53 | 110–116 ms | 3–5 |
| jitter ±15 ms (snow) | 26.2–27.4 | 1.07–1.37 | 118–128 ms | 5–7 |
| 6 Mbps into 3 Mbps (snow) | 23.0–25.4 | 0.75–1.13 | 692–832 ms | 8–12 |

Capped-link stalls fell from 2.5 s to under 0.85 s and jitter stalls from 0.9 s
to ~0.12 s. A 10% loss trigger cut stalls further on the capped link (~0.5 s)
but also cut 5% random loss to ~2 Mbps, so 20% was kept. The capped link is
still under-used; next step is to treat loss together with rising RTT as
congestion and to step resolution/FPS down.

### Input path (H6, three runs each, 20 ms delay each way)

Probe round trip on the ordered input track while pointer motion streams at

| Link | Before p50 / p95 / max | After p50 / p95 / max |
| --- | --- | --- |
| clean | 43.6–44.3 / 46.2–47.0 / 46.9–56.1 ms | 41.7–41.8 / 43.7–44.0 / 44.0–54.2 ms |
| 5% loss | 58.8–71.5 / 103.6–116.9 / 137–244 ms | 41.7–41.9 / 48.0–112.3 / 114–187 ms |

Median key latency under loss is now the RTT. The p95 tail is a probe's own

### Rate controller tuning tried and rejected (2026-10-15)

On the capped link, a gentler 15% cut (with or without 500 ms probing) moved
~25% more video (2.3–2.5 vs 1.8–2.0 Mbps) but lost ~2 FPS and lengthened
stalls slightly. Frame rate and stalls matter more for interactive use, so the
25% cut / 1 s probe stays. Revisit with a quality metric (e.g. PSNR) in the
harness rather than throughput alone.

### Client decode path at 1080p (`full_hd_clean_link_decode_path`)

Whole-run means from the headless summary, software x264 → FFmpeg decode,
NV12 output, snow at 8 Mbps. Receive→ready is almost entirely the decode call
(direct backend: decode, colour conversion and copy-out happen together);
the Rust-side copies (M1) are ~0.3 ms and were left for later.

| Slice threads | Quiet machine | Loaded (load avg ~14 on 8 cores) |
| --- | --- | --- |
| 2 (before) | 5.6–7.3 ms | 21.6–23.3 ms (+6–8 ms queueing) |
| 4 (after) | 5.1–5.8 ms | 15.5–17.2 ms (+1–2 ms queueing) |

### Host encode path at 1080p, and a rejected change (M2)

The harness now reads the host's per-encoder summary (mean copy-in and
submit-to-packet time). Software x264 at 1080p, machine under load (~13 on
8 cores): copy-in ~0.8–1.3 ms, encode ~12–14 ms.

Feeding libx264 NV12 directly (skipping the NV12→YUV420P `sws_scale`) was
inconclusive end to end under that load, so the conversion alone was timed in
thread CPU time: 0.18–0.21 ms vs 0.12–0.14 ms per 1080p frame. Saving
~0.06 ms is noise next to the encoder itself; not changed. Host-side wins
need GPU capture/conversion (DMA-BUF, M2) or hardware encode, not CPU
format juggling.

### Client decode stages at 1080p (2026-10-15, RTX 3080 host and client)

Measured with temporary per-stage timing in `ffmpeg_codec.c` (not committed),
180 frames of 8 Mbps noise at 30 FPS, ms per frame.

Before: the headless client requested RGB24 (unlike an accelerated Linux
window, which uses NV12), and NVENC emitted one slice per frame:

| Stream → decoder | decode | GPU→CPU | convert | copy |
| --- | --- | --- | --- | --- |
| NVENC → software | 7.0 | – | 3.3 | 2.0 |
| NVENC → CUDA | 1.5 | 0.8–1.0 | 8.7 (NV12→RGB24) | 2.0 |

After: four slices for every encoder; headless measures the NV12 path:

| Stream → decoder | decode | GPU→CPU | convert | copy | receive→ready |
| --- | --- | --- | --- | --- | --- |
| x264 → software | 0.9 | – | 1.0 | 0.7 | 4.3 |
| x264 → CUDA | 1.6 | 1.6 | 1.1 | 0.6 | 6.6 |
| NVENC → software | 3.5–4.5 | – | 1.6 | 0.4 | 7.5 |
| NVENC → CUDA | 1.6 | 0.8 | 0.35 | 0.4 | 4.3 |

The NV12→RGB24 conversion (6–9 ms at 1080p) is what the macOS client still
pays on every frame (M3): enabling NV12 there is likely the largest single
client win left, but needs Mac hardware to verify. Full GPU zero-copy on
Linux would remove ~1.5–2 ms of the remaining ~4.3 ms.

Tried and rejected: decoding straight into the output buffer with a plain copy
for matching formats (one copy instead of `sws` + copy). Interleaved A/B over
300 1080p frames, NVENC → CUDA: before 3.9 / 4.8 / 7.2 ms, after 6.7 / 6.4 /
6.7 ms receive→ready (machine load ~5). No measurable gain; likely per-frame
3 MB allocations dominate either way. Revisit with a reused output buffer and
a quiet machine, or skip straight to GPU-resident presentation.
